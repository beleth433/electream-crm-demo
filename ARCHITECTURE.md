# Архитектурная карта и системный дизайн Courier EBike CRM

> **Статус документа**: Живой рабочий документ (Living Architecture Document).  
> **Обязательное правило для ИИ и разработчиков**: Перед проектированием и реализацией любой новой фичи или настройки данный документ **сканируется на предмет потенциальных связей**. После реализации фичи документ **обновляется**, фиксируя новые связи и инварианты, чтобы система оставалась монолитной и непротиворечивой.

---

## 1. Концепция и ключевые принципы системы

Courier EBike CRM — специализированная ERP/CRM-система для управления парком коммерческого электротранспорта (электровелосипеды Minako Monster, Wenbox U3 Pro и аналоги), сдающегося в краткосрочную, долгосрочную аренду и **аренду с правом выкупа** курьерам служб доставки (Яндекс Еда, Купер, Самокат и др.).

### Архитектурные принципы:
1. **Связность «всё со всем» (High Interconnectivity)**: Сущности не живут изолированно. Изменение модели влияет на тарифы, байки, выкуп и склад; выдача байка влияет на статус АКБ, склад экипировки и платежный баланс; завершение ремонта списывает детали со склада и меняет статус техники.
2. **Отказоустойчивость хранения (Hybrid Persistence Engine)**: 
   - Полноценная реляционная схема в `Prisma ORM` (`schema.prisma` для PostgreSQL).
   - Встроенный независимый JSON-движок хранения (`server/data/crm_db.json`) через `server/src/repositories/db.ts` для автономного локального запуска без внешних зависимостей.
3. **Строгая типизация (End-to-End Type Safety)**: Общие типы в `client/src/types/index.ts` и `server/src/repositories/db.ts`, DTO-схемы валидации через `Zod` (`schemas.dto.ts`).
4. **Гибкость настроек без навязанных ограничений**: Никаких жестких зашитых кнопок-шаблонов сроков и интервалов; автоматические расчеты выступают помощником для пользователя, но итоговые суммы всегда остаются 100% редактируемыми вручную.

## 2. Матрица сквозных связей модулей (Cross-Dependency Matrix)

При внедрении любой новой фичи проверяйте таблицу пересечений:

| Модуль | С чем связан напрямую | Как влияет на связанные модули при изменении |
| :--- | :--- | :--- |
| **`BikeModel` (Модель байка)** | `Bike`, `Tariff`, `RentalWizard`, `Retail` | Хранит `baseRentalPrice`, `baseBuyoutPrice`, `purchasePrice`, `salePrice`. При выборе модели в тарифе или мастере выкупа подтягивает выкупную цену техники. При редактировании модели обновляет связанные байки. |
| **`BatteryModel` (Модель АКБ)** | `Battery`, `Tariff (includedBatteries)`, `RentalWizard` | Хранит вольтаж, емкость, химию, `purchasePrice`, `salePrice`. Используется как строительный блок в тарифах выкупа (`+ Добавить АКБ`) для автоматического формирования суммы комплекта. |
| **`Bike` (Электровелосипед)** | `BikeModel`, `Battery`, `Rental`, `RepairOrder` | Имеет инвентарный номер, № рамы, № мотора, пробег. Может нести на себе установленную АКБ (`installedBikeId`). При выдаче в аренду переходит в `RENTED`, при поломке в `IN_MAINTENANCE`, при выкупе в `BOUGHT_OUT`. |
| **`Battery` (Аккумулятор)** | `BatteryModel`, `Bike`, `Rental`, `RepairOrder` | Физическая батарея с серийным номером. Может быть `AVAILABLE` на складе, установлена на байк (`installedBikeId`) или выдана дополнительно курьеру (`issuedBikeId`). При выкупе велосипеда все закрепленные за договором батареи выбывают вместе с байком. |
| **`Tariff` (Шаблон тарифа)** | `BikeModel`, `BatteryModel`, `Rental`, `Payment` | Может быть универсальным (`bikeModelId: null`) или привязанным к модели. Содержит тип (`STANDARD` / `RENT_TO_OWN`), срок, сумму депозита, интервал выплат, выкупную цену и список комплектующих АКБ (`includedBatteries`). |
| **`Client` (Курьер)** | `LoyaltyTier`, `Rental`, `Payment`, `Review` | Хранит документы (РФ / СНГ: патент, миграционная карта), службу доставки, статус (`NORMAL`, `VIP`, `PROBLEM`, `BLACKLIST`). Статус `BLACKLIST` блокирует выдачу. `LoyaltyTier` дает скидки на аренду, запчасти и ТО. |
| **`Rental` (Договор аренды / выкупа)** | `Client`, `Bike`, `Battery[]`, `Outfit[]`, `Tariff`, `Payment` | Центральный узел операционного контура. Связывает клиента, байк, все выданные АКБ и экипировку. В режиме `RENT_TO_OWN` отслеживает график платежей, остаток долга (`remainingBuyoutAmount`) и автоматически переводит байк в статус `BOUGHT_OUT` при полной выплате. |
| **`Outfit` (Экипировка)** | `OutfitCategory`, `OutfitTemplate`, `Rental` | Шлемы, замки, сумки, ЗУ, держатели, муфты. Статусы `IN_STOCK`, `ISSUED`, `DAMAGED`, `LOST`. Привязываются к аренде, отображаются в печатном Акте приема-передачи. |
| **`Part` (Склад запчастей)** | `PartCategory`, `RepairOrder`, `Finance` | Учет колодок, камер, контроллеров, ручек газа. Хранит остаток, порог предупреждения (`minQuantity`), закупку и цену для клиента. При завершении ремонта автоматически списывает количество. |
| **`RepairOrder` (Заказ-наряд СТО)** | `Bike`, `Battery`, `Part[]`, `Employee`, `Rental`, `Finance` | Диагностика и ремонт техники. Разделение вины: `COMPANY_EXPENSE` (плановый износ, платит сервис) и `CLIENT_FAULT` (ДТП/залитие, счет курьеру или списание с депозита). При завершении переводит байк обратно в `AVAILABLE` и списывает запчасти со склада. |
| **`Payment` (Платежи и касса)** | `Rental`, `Client`, `Finance` | Типы платежей: `RENTAL`, `BUYOUT`, `DEPOSIT`, `REPAIR`, `REFUND`. Способы: `CASH`, `CARD`, `SBP`, `BANK_TRANSFER`. Влияет на продление срока аренды, уменьшение остатка выкупа и общую финансовую аналитику. |
| **`SimulationEngine` (Симулятор клиентов)** | Все сущности CRM | Сжимает время (1 день = 15 минут реального времени). Генерирует реалистичный входящий поток курьеров (аренда, выкуп, поломка, продление, возврат) без забивания боевой базы лишним мусором. |

## 3. Стейт-машины и жизненные циклы

### 3.1. Жизненный цикл электровелосипеда (`BikeStatus`)
```
[AVAILABLE] (Свободен на базе)
    │  ▲
    │  │ Завершение аренды / возврат
    ▼  │
[RENTED] (Выдан курьеру по договору)
    │
    ├─► [IN_MAINTENANCE] (Сломался / отправлен в СТО)
    │         │
    │         ▼ Завершение ремонта
    │    [AVAILABLE]
    │
    ├─► [BOUGHT_OUT] (Полностью выкуплен курьером — финальный статус)
    │
    └─► [DECOMMISSIONED] (Списан / тотал / утерян)
```

### 3.2. Жизненный цикл договора аренды / выкупа (`RentalStatus`)
```
[DRAFT] ──► [RESERVED] ──► [ACTIVE] (Действующий)
                               │
               ┌───────────────┴───────────────┐
               ▼ Наступила дата платежа         ▼ Полная сумма выкупа выплачена
           [OVERDUE] (Просрочен)           [BOUGHT_OUT] (Выкуплен курьером)
               │                                ▲
               ├─► Оплата внесена ──────────────┤
               │   (продление / взнос)          │
               │                                │
               └─► [PROBLEM] (Конфликт/Угон) ───┤
                                                ▼
                                            [CLOSED] (Закрыт с возвратом байка)
```

### 3.3. Жизненный цикл заказ-наряда СТО (`RepairStatus`)
```
[DIAGNOSTICS] ──► [WAITING_PARTS] ──► [IN_PROGRESS] ──► [COMPLETED]
                                                           │
                                                           ▼ (Транзакционное списание деталей,
                                                              начисление оплаты механику,
                                                              возврат байка в AVAILABLE)
```

## 4. Бизнес-правила и незыблемые инварианты (Invariants)

1. **Инвентарные номера и нумерация**:
   - Формируются по префиксам (`EV-001`, `BAT-001`, `OUTF-001`, `ORD-001`).
   - При расчете нового номера система сканирует все существующие сущности данного типа, определяя максимальный суффикс, чтобы исключить дублирование даже между разными категориями.
2. **Формула выкупа и график погашения (Rent-to-Own Schedule Formula)**:
   $$\text{Полная цена выкупа} = \text{Цена модели байка} + \sum (\text{Количество АКБ} \times \text{Цена АКБ})$$
   $$\text{Количество периодов} = \max\left(1, \operatorname{round}\left(\frac{\text{Общий срок (дней)}}{\text{Интервал выплат (дней)}}\right)\right)$$
   $$\text{Регулярный платёж} = \left\lceil \frac{\text{Полная цена выкупа}}{\text{Количество периодов} \times 10} \right\rceil \times 10 \quad \text{(округление до 10 ₽)}$$
   $$\text{Сумма регулярных платежей} = (\text{Количество периодов} - 1) \times \text{Регулярный платёж}$$
   $$\text{Финальный платёж} = \max(0, \text{Полная цена выкупа} - \text{Сумма регулярных платежей})$$
   - **Двусторонняя реактивная связь (Two-Way Binding)**:
     - При изменении общего срока $\rightarrow$ система автоматически пересчитывает регулярный платёж.
     - При ручном вводе регулярного платежа (например, 10 000 ₽ каждые 7 дней при выкупе 105 000 ₽) $\rightarrow$ система мгновенно пересчитывает необходимое количество периодов: $\text{periods} = \lceil \text{total} / \text{installment} \rceil$ и обновляет общий срок договора: $\text{durationDays} = \text{periods} \times \text{interval}$ (например, 11 платежей по 7 дней = 77 дней: 10 платежей по 10 000 ₽ + 1 финальный платеж 5 000 ₽, ровно закрывающий долг).
   - **Инвариант закрытия остатка**: Вся сумма выкупа закрывается ровно до 1 ₽. Регулярные платежи идут круглыми суммами, а финальный платеж закрывает оставшийся хвостик долга.
   - **Выравнивание срока**: Если срок в днях не делится нацело на интервал (например, 180 дн. при интервале 7 дн.), интерфейс предоставляет кнопку синхронизации срока до рассчитанного срока погашения (`↻ Синхронизировать срок`).
   - Пользователь в любой момент может скорректировать итоговую цену выкупа или размер взноса вручную; кнопка `↻ Применить расчёт` всегда позволяет вернуть точный математический расчёт.
3. **Фолбэки цен (Price Fallback Chain)**:
   - Если у модели байка не задана `baseBuyoutPrice`, система обязана подставить `salePrice`, а если и она не задана — стандартный системный ориентир (60 000 ₽), никогда не оставляя 0 ₽ без ведома пользователя.
   - То же касается цен АКБ: `salePrice` модели ➔ 25 000 ₽.
4. **Складской учет запчастей**:
   - Количество запчасти не может стать отрицательным без предупреждения.
   - При `quantity <= minQuantity` на складе и дашборде зажигается предупреждающий бейдж.
5. **Клиентский комплаенс**:
   - Клиент со статусом `BLACKLIST` блокируется на Шаге 1 Мастера выдачи аренды.
   - Клиент со статусом `VIP` получает автоматические скидки на аренду и запчасти из своего `LoyaltyTier`.

## 5. Модуль симуляции (Client Simulation Engine)

- **Назначение**: Позволяет владельцу CRM тестировать операционные процессы в ускоренном времени без засорения боевых данных.
- **Масштаб времени**: $1 \text{ день} = 15 \text{ минут реального времени}$ ($1 \text{ час} = 37.5 \text{ секунд}$).
- **Генерация событий**:
  - Приход нового курьера на краткосрочную аренду (проверка документов, подбор байка).
  - Курьер с запросом на аренду с выкупом под конкретную модель и с 2 аккумуляторами.
  - Сообщение от курьера о поломке (прокол колеса, отказ тормозов, залипание ручки газа) с созданием заказ-наряда.
  - Внесение очередного платежа по рассрочке выкупа.
  - Возврат байка и приемка экипировки.

## 6. Регламент расширения: протокол внедрения новой фичи

Перед тем, как вносить изменения в код проекта, **обязательно выполните следующий чеклист**:

```
[ ] ШАГ 1. СКАНИРОВАНИЕ СВЯЗЕЙ ПО ARCHITECTURE.MD
    - Какие сущности затрагивает новая фича?
    - С какими смежными модулями она взаимодействует (Байки / АКБ / Тарифы / Аренда / СТО / Склад / Финансы)?
    - Не ломает ли новая логика существующие стейт-машины и формулы пересчета?

[ ] ШАГ 2. BACKEND (СХЕМА, РЕПОЗИТОРИЙ, DTO)
    - Обновить schema.prisma и db.ts (добавить поля в интерфейсы).
    - Обновить schemas.dto.ts (Zod-валидация).
    - Обеспечить фолбэки для старых записей в crm_db.json.
    - Обновить Repository / Service / Controller.

[ ] ШАГ 3. FRONTEND (ТИПЫ, СЕРВИСЫ, UI)
    - Обновить client/src/types/index.ts.
    - Обновить api.ts (если есть новые эндпоинты).
    - Интегрировать UI в страницы (RentalsPage, BikesPage, RepairsPage, WarehousePage и т.д.).

[ ] ШАГ 4. СБОРКА И ВЕРИФИКАЦИЯ
    - Прогнать `npm run build` (tsc backend + tsc & vite frontend). 0 ошибок.

    - Внести новую сущность или поле в Матрицу связей (Раздел 2).
    - Если изменились переходы статусов — обновить диаграммы (Раздел 3).
    - Зафиксировать новые правила и инварианты (Раздел 4).
    - Закоммитить изменения в Git.
```
